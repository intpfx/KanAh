## 引擎与 API 23 兼容

这台盒子的系统 WebView 56 不具备所需 WASM 能力；研究过的较新 WebView 包与系统包签名不同，不能直接覆盖更新。降低 `minSdk` 或另装 Chrome 不会自动修复应用内 WebView。特供版采用可选 Gecko 后端，保持系统 WebView 不变；不能把这套方案直接套到其他代号或海外盒子的固件。

- 审查新增 UI 的实际调用，不只改 Manifest。动画状态查询、默认焦点高亮、进程和通知等 API 需要版本分支；缓存的 NIO 原子写入、符号链接检查需要相应 desugar 兼容。旧 WebView 的 XHR 与取消请求后备路径也要保留。
- Gecko 143 的桥接回复使用 `GeckoBundle`，不能拿 `JSONObject` 代替。消息带 revision / 所有者校验，过期回复、已关闭页面和旧重试不能恢复播放；保留可信页面边界，正式使用时关闭远程调试。
- WASM 转封装后的 NAL 后处理仍然需要，不能因换了浏览器内核而省掉。全屏尺寸应检查 `visualViewport`。时间、帧数推进不等于画面正确，应核对实际画面、音轨，必要时解码抓到的媒体片段。
- 小图标不要依赖设备字体覆盖率：线路下拉箭头的 Unicode 字符在盒子上显示方框，改为矢量 drawable 后正常，聚焦和非聚焦颜色分别验证。

## 生命周期、硬件解码器和窗口交接

### 浏览时保留直播

把“用户暂停”“导航静音”“首帧批准”分别建模。静音不撤销首帧批准、不主动中断直播下载；返回浏览页恢复声音但不解除用户暂停。用户暂停期间不累计播放停滞；暂停时出现致命错误，等用户主动继续后再重试。

仅资源库、详情和应用设置属于保活范围。特供版使用应用内 Activity 跟踪和 700 ms 过渡宽限，区别页面交接与真正离开应用；开始原生点播或进入外部应用时释放直播。`onStop`、`state=STOPPED`、接口的前台 `active=false` 或音轨消失，任何单项都不足以证明直播已销毁，需结合会话和重载日志判断。

Gecko 冷启动允许 60 秒；播放后 8 秒不推进显示缓冲、30 秒不推进重试，最多两次，间隔 2 / 4 秒。切台和手动重试刷新预算；后台重试继承静音状态，点播接管或离开应用取消旧任务。这些阈值是该设备的已测策略，不是通用性能保证。

### Gecko → 原生播放器

76 的首次交接出现 `OMX.amlogic.avc.decoder.awesome` 分配失败、`InsufficientResources(0x80001000)`。退出重进能播放并不能证明首次交接通过：关闭 Gecko 会话后，硬件解码器仍可能异步占用约一秒。

修复在 API 23 记录关闭直播后的 1,250 ms 释放截止时间。媒体地址解析可并行进行，创建原生播放器前只等剩余时间；仅对首帧前确定的解码器初始化资源错误允许延迟 750 ms 重试一次。保留媒体、位置和暂停意图，并以 generation / owner / player 校验及取消回调防止过期任务复活。77 和 79 均通过直播到缓存的首次播放；最终版日志没有对应解码资源错误。

### OEM 窗口顺序

78 从播放器用 `REORDER_TO_FRONT` 返回资源库时，Activity 已 `RESUMED`，但旧播放器窗口仍覆盖上层，`mCurrentFocus` 指向播放器、`mFocusedApp` 指向资源库。主线程还能响应 Activity dump，因此不能仅凭“按键无效”诊断成死锁。

79 只在 API 23 的 `MediaPlaybackActivity` 成功发出侧栏页面导航后 `finish()` 旧播放器，保留原路由 flags；启动失败、关闭菜单和普通浏览页面不结束 Activity。测试覆盖重复键、失败路径及 API 24 / 35 不受影响，实机再核对窗口焦点和 Activity 栈。

## 来源同步、TLS 与播放能力

通过应用现有配置入口同步来源，逐项比较名称、可搜索状态及完整 `url`、`header`、`ext`、`playUrl` 配置，忽略两端生成的不同内部 ID。原设备 sealed store 字节未变；最终盒子只剩尤酷 JSON、360资源、魔都资源、无损云四个真实来源，无临时源。私有配置、请求头及明文导出不得提交，导出只用于受授权的同步和比对，随后删除。

API 23 的媒体请求曾因缺少 ISRG Root X1 报 `trust-anchor-not-found`。处理是只给该系统版本的应用媒体客户端补充指定公共根，与系统信任锚取并集，双方各自完整验证证书链；保留主机名验证和证书固定规则。根证书 DER SHA-256 为 `96bcec06264976f37460779acf28c5a7cfe8a3c0aae11a8ffcee05c0bddf08c6`。不能使用 trust-all 或关闭 TLS 校验；测试应覆盖错误根、过期证书、缺失中间证书、错误主机名和 pin 不匹配。

补根后四个来源目录各返回 20 条，但目录成功不意味着每条视频可播放：

- 无损云：有上述真实遥控选集、HLS 首帧与持续播放结果。
- 魔都资源：《伟大的长征》第 01 集有限起播探测成功；未记录电视首帧实播。
- 360资源：《当妈不容易》的一条线路探测超时；后续独立请求出现 HTTP 502，不能推断整个来源失效。
- 尤酷 JSON：测试分享页返回 `REQUIRES_PARSER`，未进入原生播放。原生 HLS / MP4 支持不等于能执行分享页脚本；桌面请求缺少设备私有请求头时，也不能拿桌面 HTTP 状态直接替代设备诊断。

## 桌面、工具和系统包的边界

最终有效 HOME 候选与普通 HOME 解析均为 `com.live.tv/com.live.tv.LiveHome`。`preferred=null` 不妨碍唯一候选成为默认入口；别名的清单 `enabled=false` 也不等于实际关闭，应结合组件覆盖值（本次为 1）、查询结果和按键验证。不同固件可能先过滤 HOME 候选，写入默认关联成功不保证候选可用。

保留 `LiveHome` 与既有偏好数据，避免升级中引入多个竞争别名。旧工具包括其他应用、网络、蓝牙与遥控器、系统设置、选择默认桌面和恢复系统桌面。标准设置 Intent 不可用时，先经 PackageManager 验证再回退到厂商设置入口；无默认桌面选择器时可回退普通 HOME。

恢复桌面的顺序是先找到并成功启动可用替代 HOME，再清除自身关联和关闭自身别名。唯一桌面时必须拒绝关闭 Live。原桌面包已经移除时，应用内“恢复”按钮不能替用户重新安装缺失 APK。

本次固件拒绝 `disable-user` / `hide` CleanYourTV；检查输出和实际状态，不能只看退出码，亦不能把 `force-stop` 当持久停用。最终在用户明确要求唯一桌面后，执行 `pm uninstall -k --user 0 com.ts.launcher`，HOME 查询不再包含它。这里的 `-k` 仅表示使用保留数据参数，未验证该桌面重新安装后的数据恢复，不应承诺其数据完整。

早期系统包实验还表明：共享 UID（特别是 UID 1000）包的移除可能影响共用 keystore，不能把普通应用覆盖安装经验推广到系统清理；用户级卸载不等于删除 `/system` APK，也不等于释放系统分区空间。`GET_UNINSTALLED_PACKAGES` 等残留元数据不能替代实际可用组件查询。网络诊断可能依赖电视管家，蓝牙 HID 与语音服务也应分别验证；精简清单不能按包名批量照搬。

2026-10-21 / 22 的 CleanYourTV 唯一桌面记录属于历史；2026-10-25 最终是 Live 79 唯一桌面。原归档内的 CleanYourTV APK 和系统恢复材料随本次清理删除，不再作为可用恢复来源。未来若需更换桌面，应先另行取得可信、适配且签名正确的替代包并验证可启动，保持 Live 可用至交接完成。

## 安装验证与测试收尾

1. 安装前核对实际设备、API、包名、签名、安装 APK 摘要和持久数据；备份应核对预期文件清单、数量、内容摘要及归档可读性。本轮有效备份曾核对 113 项；失败的 `.invalid` / partial 文件不能算备份。
2. 使用同签名覆盖安装；比较 UID、首次安装时间、来源、设置和媒体缓存，区分浏览器运行缓存、播放进度等预期变化。79 的直接安装前清单因进程被 `Killed` 而不完整，不能据此宣称安装前后全文件零差异；改与上一份完整快照比较，稳定应用文件无新增 / 删除，只有期间播放产生的 `media-progress.xml` 变化。
3. 核对本地与设备 APK 摘要，不能只看版本名 / versionCode。将“构建通过”“覆盖安装成功”“首帧渲染”“持续推进”“真实声音和画面”“长期稳定”分别记录，不能互相替代。
4. 老系统的 ADB `exec-out` 二进制流和错误输出混合可能损坏归档；可先在设备写文件，再 pull 并校验。低速网络可用已验证基包生成差分，但必须核对基包、重建包和安装包完整 SHA-256；差分传输不是绕过签名验证。
5. 使用独立 ADB 服务端口并始终指定设备，避免误操作其他在线设备。API 23 上测试 instrumentation 不能正常运行时，用原生键码、UIAutomator、窗口 / Activity 状态和截图交叉验证，不把控制工具失败当成应用失败。
6. 测试期间临时延长屏幕超时，并检查真实电源状态；盒子虽接交流电仍可能报告 `mStayOn=false`，单设 `stay_on_while_plugged_in` 不足以防休眠。本轮每约 30 秒发送一次 `KEYCODE_WAKEUP`；这不保证固件重启后网络 ADB 仍开启。
7. 结束后停止唤醒循环、测试服务、日志采集和专用 ADB 服务，删除自己的测试源 / 缓存 / helper / 明文导出。恢复设置原值：本次 `stay_on_while_plugged_in=0`、屏幕超时 900000 ms、`sleep_timeout=-1`、`screensaver_enabled=0`。停用屏保失败时不要“恢复”本来未改动的包，尤其不要顺手启用原先已停用的其他系统组件。

这些结论来自本轮本地和实机材料的整理，不是跨设备保证；原始日志、截图、私有配置、恢复包和源码快照不随本文进入 Git。后续若重新开展 Android 6 维护，应重新建立独立实现和设备验收依据。
